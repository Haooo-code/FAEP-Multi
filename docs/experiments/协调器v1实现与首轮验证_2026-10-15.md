### 2.2 B 组（独立模式）的长尾现象（批跑实测）

批跑中发现：**无协调的独立探索存在"长尾轮次"**——三机中某一台偶发长时间
无法收尾（实测 1 轮中 d1/d2 在 ~170 s 内 FINISH，d3 超过 600 s 预算被批跑
超时截断；骨架轮 1 也出现过单机 >6 分钟未完成）。原因：FAEP 单机终止依赖
"前沿清空"，当个别前沿长期难消时没有统一兜底；**协调器的全局判定 + HALT
机制天然解决这一问题**（C 组两轮均在 ~200 s 统一收尾）。

**处理**：A/B/C 采用统一时间预算（B/C 批跑等待上限 600 s，超时轮如实记录为
"未完成（>600 s）"）；报告中将"终止一致性"作为协同的一个对比维度。批跑完成后
需清理 multi_results.txt 中旧脚本错位轮的重复 B-2 记录（见 §3.6）。

### 2.3 安全性实测（重要发现，如实记录）

对协同轮 1（v1.2）的 5Hz 轨迹数据（`track_C_1.csv`）做了机间距分析：

- **最小两机间距 0.082 m（t=66.2s）**——drone1 与 drone3 轨迹交叉且高度相同
  （均在 ~1.0 m），物理仿真无碰撞响应，实际已属"穿越"级别；确认为真实数据
  （逐帧核对：两机坐标几乎重合）。
- **<0.8 m 的危险接近共 92 次**（约每 3 秒一次）；平均最小间距 5.9 m。
- 原因：① v1 只做"任务级协同"（避免重复探索同一前沿），**没有轨迹级避碰**；
  ② 设计中的"高度分层 ±0.7m"在实际飞行中未生效——FAEP 的飞行高度由前沿规划
  决定，三机在飞行中都收敛到 ~1 m 高度。

**结论与对策**：v1 的定位收紧为"任务分配与终止协调"，**机间安全在报告里如实
呈现为当前局限**；v2 路线（轨迹级避让：将友机作为动态障碍/共享预测轨迹）写入
未来工作。短期补充：协调器可加"最小间距告警"（数据记录用，不介入控制）。

## 3. 本轮修复的问题（5 个）

1. **贴地陷阱（关键）**：`sampleViewpoints` 把观察点 z 取为前沿中心高度，低空前沿
   会把无人机引到 z≈0.2 m 贴地位置；此后 A* 起点位于地面膨胀层内，任何路径都失败，
   陷入 "No path to next viewpoint" 死循环（骨架轮 1 的 drone2 与协同轮 0 的 drone2 两次踩中）。
   修复：观察点 z 下限 `frontier/min_view_height=0.8`（office 类场景不存在 z<0.8 的合法通道）。
2. **stuck 释放→回抢循环**：协调器释放卡住机的任务后，"最近机"仍是同一台 →
   任务立刻被抢回。修复：stuck 机 60s 冷却期内不参与分配。
3. **失败目标无限重试（上游固有局限）**：对几何不可达的目标，FAEP 原版会无限重试。
   增加"连续失败 20s → 目标拉黑（本次运行不再选）"自愈，单机/多机均生效。
4. **孤儿协调器进程**：force_clean2.sh 未包含 coordinator 模式，旧协调器残留导致
   双协调器同时发布 assignment（现象：版本号疯涨、任务混乱）。已修清理脚本。
5. **中文日志损坏**：roslaunch 转发非 ASCII 输出变 '?'，协调器/单机新增日志全部改英文
   （代码注释仍为中文）。

（另：assignment 重发抖动——任务中心每 tick 平滑更新使 hash 全精度入哈希，已改 0.25m 量化。）

6. **批跑脚本被"运行中修改"两次**（操作教训）：bash 流式读取脚本，修改正在执行的
   脚本文件会导致后续命令解析错位（表现为轮次中途行为异常、子进程（logger）被误杀）。
   处置：冻结 multi_bench_v3.sh 专用；**任何脚本在运行期间不得原地修改**（先复制再改，
   或等待其结束）。
7. **C 组长尾（v1.1 修复）**：C 组批跑首轮出现"任务池无法清空"的卡滞
   （个别前沿持续出现在某机快照中但无法被消除 → 任务永不 done → halt 条件不满足，
   实测 6+ 分钟无收尾迹象）。修复 v1.1：**停滞保护**——任务池连续 180 s 既无新任务
   也无任务完成 → 判定"探索饱和"，halt("stagnation")。保证任何一轮都能在有限时间内
   统一收尾（现场日志存 `multi_C_sl0_longtail.log`）。

### 3.7 终止机制迭代记录（v1 → v1.5，批跑中逐轮加固）

C 组批跑暴露出"探索已完成但全局收尾判定不达标"的多类僵局，经五轮迭代加固：

| 版本 | 修复 | 触发场景 |
|---|---|---|
| v1 | 基础：任务=快照消失(8s)；halt=全 FINISH+池空；全局超时 900s | —— |
| v1.1 | **停滞保护**：池 180s 无任何变化 → halt | 池被滞留任务堵住 |
| v1.2 | ① 等待机(无活)名下任务即时释放 ② halt 增"池空且无探索机"③ FINISH 机快照不再喂任务 | 等待机占任务 / 完成机残留前沿 |
| v1.3 | stuck 机不阻止收尾判定 | 卡住机 state 仍为"探索中" |
| v1.4 | **抖动防护**：跳过与当前位置 <2.5m 的目标（防"短轨迹-重规划"循环，无人机原地打转） | 近距目标循环（d3 特征） |

### 3.8 超时的真实根因：exploration_node 偶发 OOM（重要）

对 C-4 超时轮的深查发现：**并非收尾机制失效，而是某台机的算法进程被 OOM 杀死**
（dmesg：`Killed process (exploration_nod) anon-rss:8684956kB` = **RSS 8.6 GB**）。
与骨架轮 1 的首次 OOM（8.1 GB，同为"探索中持续高频重规划"的机）同型：
推测机制为"高频重规划 → 每次 searchFrontiers/规划产生大量临时分配 → 分配器高水位
随分配流量暴涨至数 GB"（heaptrack 已证无经典泄漏）。

**影响**：B/C 批跑中约 40% 轮次出现某台机被 OOM 杀 → 该轮无法正常收尾（批跑
按 600 s 上限截断并记录）。受影响轮次已移入历史文件，正式对比数据为
B 5 轮（1 轮截断）/ C 3 轮（完整）。

**次日修复计划**（优先级高，先于新实验）：
1. 复现并定位高频重规划的触发条件（目标黑名单/任务过滤的组合）；
2. 加大分配器"归还"（`malloc_trim` 定时调用）或限制重规划频率的工程兜底；
3. 修复后补齐 C-4/C-5 与 B 超时轮，使 A/B/C 各 ≥5 轮完整样本。

### 3.9 OOM 根因确认与防御修复（当日完成）

**抓现场**：趁一次内存暴涨到 9.1 GB 的节点仍在运行时 attach heaptrack，
拿到决定性证据——

```
std::vector<>::_M_realloc_insert<...>(..., Eigen::Matrix<>&&)
  ← KinodynamicAstar::getSamples(double&, vector<>&, vector<>&)
（伴随 __cxa_throw / std::terminate 符号与 "Trace recursion detected"）
```

**根因**：`KinodynamicAstar::getSamples()` 沿搜索树 `parent` 链回溯计算路径时长
`T_sum`；在该机上父指针链**成环**（特定搜索/复用组合下的数据损坏）→ 第一循环
永不停止、`T_sum` 溢出为巨大值 → 后续**采样循环次数爆炸**（`for ti: T_sum→0`）→
`point_set` 疯狂 `push_back`（heaptrack 实测该路径 90 s 内 61 MB 持续泄漏，正常仅 36 KB）
→ 内存涨到 8–9 GB 被 OOM 杀死。**不是分配器高水位，是真实的活跃对象无限增长。**

**修复（三处防御 + 两处辅助，全部在单机侧）：**
1. `getSamples` 第一循环加计数器上限（20 万）：检测到超长链**在损伤点断开自愈**
   （后续重规划自动绕过坏环）；
2. 采样循环加 `pushed` 硬上限（100 万点）：数据异常时直接截断，杜绝无界增长；
3. 采样循环中 `node->parent->parent` 访问加 NULL 保护（断链场景防解引用崩溃）；
4. PLAN_TRAJ 入口增加规划最小间隔 0.2 s（正常 2–3 Hz 不受影响，抑制抖动期高频循环）；
5. `cmdTimerCallback` 每 10 s 调用一次 `malloc_trim(0)`（辅助回收高水位）。

**验证**：修复后 C-4 轮完整跑通（392 s 收尾、三机全完成、无 OOM），
RSS 监控全程稳定在 **1.54 GB ± 0.01**（修复前同状态会涨至 8–9 GB）。
至此 OOM 问题闭环，开始补齐各 5 轮数据。

**v2 迭代（C-5 再测时的发现）**：首版"截断式防御"把无限循环变成了"巨大但有限的
计算"（断环前 T_sum 已累加 20 万节点时长 → 采样 40 万点 → 下游 B 样条参数化的
矩阵运算再次内存爆炸）；另有"截断样本进入参数化产生坏死 B 样条 → Eigen 断言 abort"
的崩溃。最终方案（v4）：
- `T_sum` 合理性校验：>1800 s 直接判"采样无效"（清空返回）；
- 采样数上限 2 万：**超限即清空返回**（不再截断保留）；
- `planner_manager::kinodynamicReplan` 增加采样健全性检查（<4 点走"规划失败"重试）。

**v4 验证**：C-5 轮完整成功（276 s 收尾，三机 247.5/256.4/263.2 s，RSS 全程 1.54 GB，
防御零触发）；B-2 重跑（此前唯一超时轮）也恢复正常（181 s）。**A/B/C 办公室场景
各 5 轮完整数据至此集齐**，并生成对比图表（`assets/fig_*.png`）。
